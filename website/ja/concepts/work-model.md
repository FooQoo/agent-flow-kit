# Work Model

*AFK がどのように仕事を構造化し、「次に何を行い、何をもって完了とするか」を明確にしているかを説明します。*

> 仕事を構造化して、次に何を行い、何をもって完了するかを明確にする。

## 4 つの基本要素

AFK はすべての仕事を `.afk/` 配下の 4 つの要素で扱います。

| 要素 | 役割 | 保存先 |
| --- | --- | --- |
| **Request** | 初回の依頼と、途中の追加・変更依頼。目的と意図の記録。 | `.afk/requests/NNN.md` |
| **Plan** | 依頼を実現するための計画、タスク構成・順序、プラン全体の完了条件。 | `.afk/plans/NNN-rMMM.md` |
| **Task** | 実行可能な作業単位。前提関係、完了条件、実行履歴、結果の証跡を持つ。 | `.afk/tasks/NNN.md` |
| **Question** | AI から人間への確認質問と、確定された人間の回答。 | `.afk/questions/NNN.md` |

## 仕事のライフサイクル

```text
  Request ──▶ Plan（リビジョン）──▶ Task（実行）──▶ 検証・完了
                   │     ▲             │
            （必要時）   │             │（必要時）
                   ▼     │             ▼
                  Question ────────────┘
                   ▲
  追加 Request ──（完了済みタスクは証跡として残し、残タスクを再計画）
```

1. **Request**: 依頼内容を `.afk/requests/` に記録します。
2. **Plan**: ドラフトを用意し（`update_plan / prepare`）、プランとタスクを Markdown で記述して確定します（`update_plan / commit`）。
3. **Clarify（必要時のみ）**: 人間の判断が必要な場合、質問を `.afk/questions/` に用意して確認します。回答が必要な作業は待機し、回答を新しい計画リビジョンに反映してから進みます。
4. **Execute**: 前提を満たしたタスクから順に着手し（`start_next`）、`## Acceptance` の全項目を確認して `## Result` に証跡を書き、`finish_task` で完了にします。
5. **Complete**: 有効なタスクがすべて `Done` になったら、プラン自身の完了条件を確認して `update_plan / finish` で完了します。

## 計画のみと実行依頼の区別

AFK はすべての仕事に一律の承認ゲートを挟むのではなく、依頼の意図に応じて状態を分けます。

- **計画のみ（`execute: false`）**: ドラフト確定後も `Backlog` に留まり、人間が「進めて」と開始を指示する（`update_plan / authorize`）まで実行を始めません。
- **直接実行（`execute: true`）**: 確定と同時に `Todo` へ進み、不明点がなければそのまま実行を開始します。

## 完了条件（Acceptance conditions）

すべての Plan と Task は、着手前に順序付きの箇条書き（`## Acceptance`）を持ちます。ドラフト確定時に仕様の SHA-256 ハッシュが記録され、完了時には全項目の 1 始まり番号（`[1, 2, ...]`）の検証と、空でない `## Result` の記載が必須になります。

## 進捗と次の作業の判定

AFK は SQLite の状態から、未回答の質問・未反映の依頼や回答・公開中ドラフト・進行中タスク（`Doing`）・着手可能な `Todo` タスク・最終検証の優先順位で「次の行動（`NextAction`）」を決定論的に返します。全 10 種類の詳細は [MCP リファレンス](/ja/reference/mcp#progress-と-nextaction-の構造) を参照してください。

## 変更への適応（再計画）

作業の途中で追加依頼や方向修正が入った場合：

1. 新しい指示を追加 Request として記録します。
2. 新しいリビジョンのドラフトを作成し、不要になった未完了タスクを `remove`、新しいタスクを `add` で差し替えます。
3. すでに完了した（`Done`）タスクは消されず、検証済みの証跡として残ります。

## 作業の再開

依頼・計画・タスク・質問・引き継ぎメモ（handoff）が `.afk/` に保存されているため、別セッションでも `open_plan` で状況と引き継ぎメモを読み、前のワーカーが停止していることを確認したうえで `start_next`（必要時は `take_over: true`）から安全に再開できます。
