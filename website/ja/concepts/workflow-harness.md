# Workflow Harness

*AFK の設計思想を理解したい方向けに、「なぜハーネスなのか」「Skill だけの仕組みと何が違うのか」を説明します。*

> AI が仕事をする。AFK がその遂行を支える。人間が主導権を握る。

## AI の能力と「仕事の遂行」の違い

現在の AI エージェントは、個別のコード生成や調査・テスト実行に高い能力を持っています。一方で、まとまった依頼を最初から最後までやり遂げるには、目的の保持・作業順序・判断の確認・完了検証・セッションをまたぐ継続といった「進め方の支え」が別途必要になります。

## ハーネスが支えるもの

AFK は仕事の遂行に必要な次の 6 点を支えます。

- **目的** — 初回の依頼と途中の追加依頼をそのまま記録する。
- **次の行動** — 会話ログの記憶に頼らず、状態から次に取るべき操作を導く。
- **判断基準** — 人間の確認が必要な質問を独立して扱い、回答の反映を強制する。
- **進行状態** — `Backlog` / `Todo` / `Doing` / `Done` を SQLite で決定論的に管理する。
- **完了条件** — 着手前に基準（`## Acceptance`）を持ち、完了時に検証番号と `## Result` の記録を求める。
- **人間への報告** — 会話ターンの末尾に Stop Hook で現在状況を簡潔に伝える。

## Structure / Guidance / Continuity

依頼・計画・タスク・質問という構造化は目的そのものではなく手段です。ハーネスの役割は、状態に基づく **進行支援（Guidance）** と、ターンやセッションを超えた **状態の継続（Continuity）** にあります。

```text
  Human（目的・判断・方向修正）
     ▲                                  ▲
     │ 通常の会話                        │ ターン末尾の進捗報告（Stop Hook）
     ▼                                  │
  AI Agent（推論・計画・実行・検証）
     ├── 標準ツール（Read / Write / Edit / Shell）──▶ プロジェクト & .afk/*.md
     └── AFK（MCP ツール / Hooks）──────────────────▶ .afk/afk.db（状態・順序）
```

*※ 上図は責務の分離を表す概念図であり、AFK が人間と AI のすべての通信を中継するプロキシではありません。*

## State-aware harness（なぜ Skill だけではないのか）

Skill は行動指針を与えられますが、会話が長くなると薄れたり、セッションが変わると文脈がリセットされたりします。AFK は簡潔な Skill に加えて、ローカルの SQLite（`.afk/afk.db`）と Markdown（`.afk/*.md`）を 6 つの MCP ツールで扱うことで、状態遷移・依存関係・仕様ハッシュ検証・進捗集計を Rust 側で決定論的に支えます。

## Extend, not replace

**既存の AI エージェントを置き換えるのではなく、仕事の進め方を拡張する。**

AFK は利用中のモデル、クライアント（Claude Code / Codex 等）、標準ファイル操作ツール、既存の権限境界をそのまま維持します。本文の読み書きはエージェントの標準ツールに任せ、AFK は状態と整合性の管理に徹します。

## Limits（ハーネスの限界）

AFK は仕事の遂行を支えるための仕組みですが、以下を保証するものではありません。

- Skill は行動の指針であり、モデルが常にすべての規則に従うことを強制する機構ではありません。
- `.afk/` 以外のファイル編集やシェル実行をすべて捕捉・制御するものではありません。
- モデルの技術的判断の正しさや、あらゆるタスクの自律完遂を保証するものではありません。
